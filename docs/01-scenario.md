# 场景定义：B2B 办公设备与耗材订单履约场景

## 1. 业务背景

本场景模拟一家中型 **B2B 办公设备与耗材经销企业**（主营打印机、复印机、投影仪及配套硒鼓、墨盒、复印纸）。

随着业务发展，公司在不同时期独立上线了三套核心业务系统：

| 源系统 | 负责部门 | 管辖范围 | 典型表 / 文件 |
| :--- | :--- | :--- | :--- |
| **CRM** | 销售部 | 销售团队、客户线索与客户账号、客户分级 | `owners.csv`, `accounts.csv` |
| **ERP** | 商务 / 财务部 | 客户主数据、产品与品类码表、销售订单及明细 | `customers.csv`, `products.csv`, `category_codes.csv`, `sales_orders.csv`, `order_items.csv` |
| **WMS** | 仓储物流部 | 实际出库发货单、承运商、签收状态 | `shipments.csv` |

数据快照基准日固定为 **`2026-11-23`**（用于保证所有“近 30 天”“是否逾期”等业务查询结果完全可复现）。

---

## 2. 为什么需要 Ontology？（真实痛点）

三套系统各自为政，导致业务部门想回答一个看似简单的问题都异常痛苦：

1. **同一实体在多系统里分裂（实体对齐难）**
   - CRM 用 `account_id`（`ACC-1001`）和简称（`云帆科技`），ERP 用 `customer_no`（`C0001`）和工商全称（`杭州云帆科技有限公司`）。
   - 存在**名称相似但并非同一家**的企业（`云帆科技` vs `新云帆网络`），直接做模糊匹配会误合并。
   - 存在**企业更名**导致名称完全脱节（CRM 仍是旧名 `博思咨询`，ERP 已更新为 `远东管理咨询有限公司`，只能通过统一社会信用代码或人工映射对齐）。
   - 存在**单边系统记录**（只在 ERP 下过单但 CRM 没建档，或只在 CRM 跟进但从未下单）。
2. **同一概念语义口径不统一（语义混乱）**
   - CRM 的客户等级写成 `VIP`、`vip`、`大客户`、`普通`、`一般客户`、`普通客户`、`潜在客户` 或空值。
   - “**已发货**”到底听谁的？ERP 的订单状态同步经常滞后（仍显示 `A-待发货`），WMS 里还有 `待出库`（仅打单备货，并未真正交寄）。
3. **跨系统关联键与数据格式不规范（脏数据常态化）**
   - WMS 里部分发货单的订单号丢失了连字符（`SO20261105905` vs `SO-20261105-905`）。
   - ERP 订单日期以 `YYYYMMDD` 为主，却混入 `2026/10/15`；明细金额混入带千分位逗号的字符串 `"12,800.00"`；部分订单缺少承诺交付日。
   - 存在引用了不存在订单号的孤立发货单（`DN-20261118-901 -> SO-20261118-777`）。
4. **层级分类主数据失真**
   - 产品表里存在未维护分类、分类码与分类名冲突、引用不存在分类码、直接挂在一级非叶子分类上的商品。

## 3. 核心业务能力问题（Competency Questions, CQs）

在本体工程（Ontology Engineering）中，**不能脱离业务问题空想概念模型**。我们用以下 4 个典型业务问题来驱动并验收后续的 Ontology 设计：

### CQ1：高价值客户履约预警（跨三系统 + 口径裁决）
> **问题**：截至 `2026-11-23`，近 30 天内（`2026-10-25` ~ `2026-11-23`）下单的 **VIP 客户**，有哪些**已过承诺交付日、未取消、且实际尚未有效发货**的订单？对应的客户名称、销售负责人及所属团队是谁？

- **核心业务语义裁决**：
  - `VIP 客户`：仅指 CRM 等级归一化后为 `VIP`（含 `VIP`/`vip`，不含 `大客户`）的客户。
  - `有效发货`：以 **WMS 为事实源**（而非滞后的 ERP 状态），且 WMS 状态必须为 `已出库` 或 `已签收`（`待出库` 不算有效发货）。
- **预期精准命中（4 张）**：`SO-20261103-901`、`SO-20261106-903`、`SO-20261110-902`、`SO-20261112-904`。

### CQ2：跨系统客户 360° 全景视图（实体解析）
> **问题**：以“真实世界客户（Party / Customer）”为统一锚点，汇总其 CRM 等级与归属销售、ERP 历史有效订单数与总金额、WMS 履约准时率，并标注哪些客户仅在单一系统存在。

### CQ3：按产品大类聚合销售与分类合规审计（层级推理）
> **问题**：沿产品分类树向上汇总一级大类（`办公设备` vs `耗材`）的销售额，同时列出所有无法可靠归类的异常商品及其缺陷原因。

### CQ4：跨系统数据一致性审计（规则约束）
> **问题**：自动发现源系统间的业务规则违例——包括 ERP 状态滞后于 WMS 实际出库、WMS 悬空发货单、订单缺少承诺交付日、日期/金额格式异常等。

---

## 4. 后续 Ontology 构建路线图

1. **阶段一（当前已完成）**：定义业务场景与 CQ1–CQ4，生成带真实数据缺陷的 CRM / ERP / WMS 源数据。
2. **阶段二（概念与本体建模）**：抽象出核心对象类型（`Party/Customer`、`SalesOwner`、`Product`、`ProductCategory`、`SalesOrder`、`OrderLine`、`Shipment`）、对象关系（Links）、属性及业务规则/语义定义。
3. **阶段三（语义映射与实体解析）**：编写从源系统 CSV 到 Ontology 实例层的转换、归一化与实体对齐规则（保留血缘与来源映射，不破坏原始系统）。
4. **阶段四（查询验证与约束校验）**：基于 Ontology 回答 CQ1–CQ4，并与源系统预期埋点逐一交叉核验。
5. **阶段五（Action 与 AI Agent 接入）**：为 Ontology 绑定业务动作（如“逾期订单催办 / 派发销售预警任务”），开放标准语义接口供应用或大模型调用。
