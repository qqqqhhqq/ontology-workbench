## 2. 对照实验：没有 Ontology 直接查源表会怎样？

以 **CQ1（近 30 天 VIP 客户逾期未有效发货订单）** 为例，对比三种查法：

| 查询方式 | 命中结果 | 准确率 / 召回率 | 踩中的企业真实数据陷阱 |
| :--- | :--- | :---: | :--- |
| **朴素直查 A**<br>（按客户名 JOIN + `customer_level=='VIP'` + 信 ERP 状态） | `[]`（0 张） | 0% / 0% | CRM 存简称（`云帆科技`）、ERP 存全称（`杭州云帆科技有限公司`），直接 JOIN 全部丢失 |
| **朴素直查 B**<br>（用信用代码 JOIN + 忽略大小写 + 裸单号左连 WMS） | `SO-20261028-001`、`SO-20261103-901`、`SO-20261105-905`、`SO-20261110-902` | **50% / 50%** | 1) **漏报 904**：星辰设计 CRM 缺信用代码，无 Crosswalk<br>2) **漏报 903**：把 WMS `待出库` 误当成有效发货<br>3) **误报 905 & 1028-001**：WMS 单号丢失连字符导致左连失败 |
| **Ontology 语义查询**<br>（`c.is_vip=1 AND o.is_overdue_unshipped=1`） | **`SO-20261103-901`、`SO-20261106-903`、`SO-20261110-902`、`SO-20261112-904`** | **100% / 100%** | 实体解析、词表归一化、订单号修复与 WMS 事实源裁决已在本体层一次性收口 |

> **关键结论**：即使是经验丰富的分析师（朴素查法 B，已经主动想到用信用代码 JOIN、忽略大小写、避开已取消单、查 WMS 发货表），在真实企业脏数据面前依然会出现 **50% 误报 + 50% 漏报**；而把这些规则沉淀到 Ontology 后，业务查询只需寥寥几行，且所有下游报表与 AI Agent 共享同一套 100% 一致的口径。
