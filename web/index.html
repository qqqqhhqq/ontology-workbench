架构范式本质差异总结：Text-to-SQL vs Operational Ontology

什么时候用 Text-to-SQL，什么时候必须上 Operational Ontology？
对比维度 Text-to-SQL（直连物理表） Operational Ontology（语义本体 + 动作层）
底层视角 面向存储与物理表（10 张分散的 crm_*/erp_*/wms_* 裸表） 面向真实业务世界（8 个统一对象 + 7 类显式语义边）
实体对齐与业务口径 每次提问都靠 LLM 临场猜 JOIN 条件和口径（易漏 ACC-1006、混淆 VIP/大客户、错把 待出库 当已发货） 三级实体解析 + 受控词表 + WMS 权威裁决一次性沉淀在 schema.yaml，全企业与 AI 共享唯一真相
真实脏数据容错 极易静默算错（例如 SQLite SUM(CAST('12,800.00' AS REAL)) 静默截断为 12.0，直接少算 ¥12,788 而不报错！） 清洗与校验解耦：脏数据标准化入库同时显式挂 DataQualityIssue（DQ-001~012），金额 100% 守恒
Token 成本与延迟 每题需多轮试探码表/样本（实测 CQ1–CQ3 平均每题 7.7 轮、11.3 条 SQL、20,950 Tokens），极易触发网关限流 429 语义工具一步直达（实测 CQ1–CQ3 平均每题 2 轮、1 次 MCP 调用、4,489 Tokens），节省约 79% Token、快 2.4 倍
业务闭环与安全性 本质是只读查询；一旦放开 SQL 写权限极具灾难风险，无法做业务规则拦截 原生操作型闭环：EscalateOverdueOrder / FixProductCategory 带前置守卫、dry_run、HITL 审批与不可变审计账本
适用场景边界 适合单一干净数仓/宽表的临时探索性 BI 分析（Ad-hoc 自由切片） 适合跨异构系统运营决策、高合规指标口径统一、以及需要可靠且可控地执行业务动作的 AI Agent
